# PLAN — Portfolio → Portfolio + Beat Store

**Status:** approved plan, not yet implemented (implementation starts on a future session)
**Date:** 2026-08-21

Evolves the static virus404beats site into a **portfolio + beat store**: dynamic music catalog (YouTube + uploaded beats), a hidden admin dashboard with layered auth, Cloudinary-hosted streamable beat previews, and a manual negotiation-based buy flow. All free tiers.

---

## 1. Vision

| Capability | Today | Target |
|---|---|---|
| Music | Static config lists (`beats[]`, `releases[]`) | DB-backed, editable from dashboard; YouTube embed streaming; top-10 quick-play strip |
| Store | — | `/beats` sub-page: priced beats, streamable tagged previews, Buy buttons (Email + WhatsApp) |
| Works page | — | `/works` two-column: YouTube column + uploaded MP3s column (no downloads, stream only) |
| Admin | — | Hidden `/admin`: Google auth → OTP → dashboard (music-first CRUD) |
| Media | static images | Cloudinary (audio + covers), YouTube embeds |
| Buy flow | — | Prefilled email **and** WhatsApp message (beat ID, title, price) → manual negotiation → you deliver full file |

No music is downloadable from the website; previews are streamed and **tagged** so even a rip is worthless.

## 2. Locked architecture decisions

- **Hosting:** Vercel (Hobby, free)
- **Database:** Turso (libSQL, SQLite) + **Drizzle ORM** + migrations. Free tier is generous (500 DBs, GB-scale storage) — plenty for single-admin data. Neon/Supabase are viable but add cost/complexity we don't need.
- **Auth:** hand-rolled Google OAuth (server-side code exchange, plain `fetch` — no Auth.js dependency risk vs Next 16 breaking changes) + session as signed HttpOnly JWT cookie (`jose`). *Fallback noted: Auth.js v5 if compat check passes.*
- **OTP:** 6-digit, hashed (`sha256` + salt), 10-min expiry, max 5 attempts, rate-limited. Sent via **Resend** (free tier 100/day). **Decision point (suggestion #1):** use a **different email than the Google account** for OTP delivery — same inbox = no added security. TOTP app (Google Authenticator) is the stronger alternative; document whichever you pick.
- **Cloudinary:** **one upload per beat** (suggestion #3) — clean file only. Tagged/looped preview generated by Cloudinary **delivery transformation** (watermark + loop) at stream time. Signed URLs + fetch protection deter hotlinking; honest note: absolute no-download is impossible client-side, the real protection is the tag.
- **YouTube:** manual video-ID entry in dashboard (no API key). Embeds via `youtube-nocookie.com`; thumbnails via `i.ytimg.com/vi/{id}/hqdefault.jpg`. **Lite-youtube pattern** (suggestion #7): thumbnail + click-to-load, one shared player swapping sources for top-10 quick-play.
- **Rendering:** public DB-backed pages use **ISR `revalidate: 60`** (suggestion #4); hero and static sections stay fully static/prerendered.
- **Rate limiting:** Vercel built-in function rate limits + in-DB attempt counter (suggestion #6). No Upstash.
- **Config compatibility:** `src/config/site.ts` remains the default/fallback; DB rows override at render (server components merge).
- **No autoresponder** (suggestion #5): the prefilled buy message already carries your WhatsApp/Instagram; you reply manually.

## 3. Security layers (as specified + hardening)

1. `/admin` route unlinked anywhere (obscurity layer 1)
2. Google OAuth — callback rejects any email not in `ADMIN_EMAILS` env (layer 2)
3. OTP emailed after Google login (layer 3; see decision point §2)
4. Every `/api/admin/*` route verifies JWT session cookie **and** OTP-verified claim
5. Rate limits on auth endpoints (Vercel native + in-DB counters); no user enumeration (same response whether email allowed or not)

## 4. Data schema (Turso + Drizzle)

- `beats` — id, slug, title, meta, year, price, currency, cover, cloudinaryPublicId, youtubeId (nullable), isTop, order, status (draft|published), createdAt, updatedAt
- `works` — id, kind (youtube|uploaded), youtubeId?, cloudinaryId?, title, meta, year, order, status
- `otps` — id, email, codeHash, attempts, expiresAt, createdAt
- `content_overrides` — key, value(json), updatedAt — typed fields only: services, hero, about (NOT a generic editor, suggestion #2)
- `audit_log` — id, action, detail, createdAt (Phase 4)

## 5. Env vars

`GOOGLE_CLIENT_ID` · `GOOGLE_CLIENT_SECRET` · `ADMIN_EMAILS` (comma list) · `OTP_EMAIL` (separate inbox) · `RESEND_API_KEY` · `TURSO_DATABASE_URL` · `TURSO_AUTH_TOKEN` · `CLOUDINARY_CLOUD_NAME` · `CLOUDINARY_API_KEY` · `CLOUDINARY_API_SECRET` · `AUTH_SECRET` (JWT signing) · `SITE_URL`

## 6. New routes

- Pages: `/beats` (store) · `/works` (two-column) · `/admin` · `/admin/login` (Google → OTP) · `/admin/dashboard` (tabs: Beats, Works, Content)
- API: `/api/auth/google` · `/api/auth/callback` · `/api/auth/logout` · `/api/auth/otp/request` · `/api/auth/otp/verify` · `/api/admin/beats` (CRUD) · `/api/admin/works` (CRUD) · `/api/admin/content` · `/api/admin/cloudinary/sign` · `/api/public/beats` · `/api/public/works`

## 8. Buy flow (documented optimal manual flow)

1. User on `/beats` clicks **Buy** → two buttons: **Email** (mailto: subject `Beat Purchase: {title} ({id})`, body with beat ID, title, price, license note) and **WhatsApp** (`wa.me` with the same info prefilled)
2. You receive it and negotiate manually (price, license, usage)
3. On agreement you deliver the full file via WhatsApp/email/Drive — full files never touch the site
4. Preview remains the tagged/looped Cloudinary stream; nothing downloadable site-side

## 9. Free-tier budget (everything fits)

Vercel Hobby · Turso free · Cloudinary free (~25 GB media) · Resend free (100 emails/day — OTP usage is tiny) · Google OAuth free. No paid upgrades expected.

## 10. Out of scope (deliberately)

- Generic page editor / drag-drop editing
- Payments integration (UPI/card) — manual negotiation by design
- Public accounts/user auth
- Autoresponder bots
- YouTube Data API sync
